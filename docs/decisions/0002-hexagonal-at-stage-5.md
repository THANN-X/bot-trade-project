# 0002 — Hexagonal (ports & adapters) เต็มรูปแบบ: ทำตอนฉาก 5 ไม่ใช่ตอนนี้

**วันที่:** 2026-09-25 · **สถานะ:** ตัดสินใจแล้ว รอถึงฉาก 5

## Hexagonal คืออะไร (ย่อ)
แบ่งระบบเป็นสองส่วน:
- **แกนกลาง (core)** — ตรรกะที่สำคัญที่สุด ไม่รู้จักโลกภายนอกเลย
  ไม่รู้ว่าข้อมูลมาจากไฟล์หรือเน็ต ไม่รู้ว่าคำสั่งไปที่ไหน
- **ขอบนอก (adapters)** — โค้ดที่คุยกับโลกจริง: อ่านไฟล์, ต่อ API, เขียนฐานข้อมูล

ระหว่างสองส่วนมี **port** เหมือนปลั๊กไฟที่แกนกลางกำหนดรูปร่างไว้
อะไรก็ได้ที่รูปร่างตรงก็เสียบได้ และ **ลูกศร import ชี้เข้าหาแกนกลางเสมอ**

## จับคู่กับบอทเทรด
| ส่วน | ในโปรเจกต์นี้ |
|---|---|
| แกนกลาง | `strategies/` + `risk/` + loop หลัก |
| port | "แหล่งข้อมูลราคา" (`MarketData`), "ที่ส่งคำสั่ง" (`Broker`) |
| adapter ชุด backtest | อ่าน CSV + โบรกเกอร์จำลองที่คิดค่าธรรมเนียม/slippage |
| adapter ชุด live | WebSocket ของ exchange + ส่งคำสั่งจริงผ่าน ccxt (testnet) |

backtest กับ live เป็นแค่ "ชุดปลั๊กคนละชุด" ที่เสียบเข้าแกนกลางตัวเดียวกัน
→ โค้ดที่ทดสอบกับโค้ดที่รันจริงเป็นตัวเดียวกัน

## โครงปัจจุบัน (ฉาก 1–4) ต่างจากเต็มรูปแบบตรงไหน
- strategy เป็นฟังก์ชันบริสุทธิ์แล้ว แต่ **ยังไม่มี port ชัดเจน**
- loop ที่ "อ่านราคา → เรียก strategy → ส่งคำสั่ง" ยังเขียนแยกในแต่ละฝั่ง (`backtest/engine.py` และ `live/` ในอนาคต)

## รูปร่างเมื่อทำเต็มรูปแบบ (ฉาก 5)
ย้าย loop เข้าแกนกลาง แล้วกำหนด port เป็น interface:

```python
from typing import Protocol

class MarketData(Protocol):
    def next_bar(self) -> Bar | None: ...

class Broker(Protocol):
    def place_order(self, side: str, size: float) -> None: ...

def run(strategy, risk, data: MarketData, broker: Broker):
    while (bar := data.next_bar()) is not None:
        signal = strategy.on_bar(bar)
        order = risk.evaluate(signal, bar)   # ขนาดไม้ + kill switch — กลยุทธ์ไม่กำหนดขนาดเอง
        if order:
            broker.place_order(order.side, order.size)
```

`run()` ตัวเดียวใช้ได้ทั้งสองโหมด ต่างกันแค่ส่ง `CsvData` + `SimBroker`
หรือ `ExchangeData` + `ExchangeBroker` เข้าไป

(ต่างจากตัวอย่างต้นฉบับตรงที่มี `risk` คั่นกลาง ตามกฎ "ทุกสัญญาณผ่าน risk/ ก่อนเสมอ")

## ทางเลือก: สะพานจาก `generate_signals(df)` ไป live โดยไม่เปลี่ยน interface
ตัวอย่างข้างบนใช้ `strategy.on_bar(bar)` แต่ interface ตอนนี้คือ `generate_signals(df)`
ถ้าเปลี่ยน interface ตอนฉาก 5 ต้องเขียนกลยุทธ์ใหม่ทุกตัว

**ทางเลือก:** adapter ฝั่ง live เก็บ DataFrame ของแท่งล่าสุดเป็นหน้าต่างเลื่อน (rolling window)
ทุกครั้งที่แท่งใหม่ปิด → เรียก `generate_signals(window)` → ใช้สัญญาณของแท่งสุดท้าย
กลยุทธ์ไม่ต้องแก้เลย

### ข้อสังเกต: `test_lookahead` พิสูจน์ได้แค่ครึ่งเดียว
- `test_lookahead` ตรวจการตัด **ส่วนท้าย** (อนาคต) → ครอบคลุมฝั่งท้ายของหน้าต่าง live
- แต่หน้าต่าง live ตัด **ส่วนหัว** (อดีตเก่า) ด้วย ซึ่ง test นี้ไม่ได้ตรวจ

ปัญหาคือ **warm-up ของ indicator**: ค่า indicator ช่วงต้นหน้าต่างยังไม่เท่ากับค่าที่คำนวณจากข้อมูลเต็ม
- **SMA** ใช้ข้อมูลย้อนหลังแค่จำนวนแท่งที่กำหนด → ค่าตรงเป๊ะเมื่อมีข้อมูลพอ
- **EMA** จำอดีตทั้งหมด (น้ำหนักลดลงเรื่อย ๆ แต่ไม่เป็นศูนย์) → ตัดหัวเมื่อไหร่ค่าเพี้ยนเสมอ ได้แค่ "เพี้ยนน้อยพอ"
  - น้ำหนักของอดีตที่ถูกตัดเหลือ ≈ (1 − α)ⁿ โดย α = 2 / (span + 1)
  - span 50 → ต้องมี ~173 แท่ง (≈ 3.5 × span) น้ำหนักที่ถูกตัดจึงเหลือต่ำกว่า 0.1%
  - `pandas.ewm(adjust=True/False)` ให้ค่าช่วงต้นต่างกัน ต้องใช้แบบเดียวกันทั้ง backtest และ live

### ขนาดหน้าต่างขั้นต่ำ
| กลยุทธ์ / indicator | ขั้นต่ำ | เหตุผล |
|---|---|---|
| SMA cross 20/50 | 51 แท่ง | SMA 50 ต้องมี 50 แท่ง + แท่งก่อนหน้า 1 แท่งเพื่อตรวจว่า "ตัดกัน" |
| EMA span N | ~3.5 × N แท่ง (ความคลาดเคลื่อน < 0.1%) | EMA ไม่มีจุดที่ตรงเป๊ะ |
| ATR period N (stop แบบ atr) — **ใช้ค่าเฉลี่ยธรรมดา** | N + 1 แท่ง (N = 14 → **15 แท่ง**) ค่าตรงเป๊ะเมื่อครบ | True Range ต้องใช้ close แท่งก่อนหน้า (+1) · เลือกค่าเฉลี่ยธรรมดาแทน Wilder (α = 1/N, ~6.6 × N ≈ 94 แท่ง และไม่มีจุดที่ตรงเป๊ะ) เพราะตรวจมือได้และไม่ต้องห่วงหน้าต่าง live — ค่าจึงต่างจาก ATR บน TradingView ที่ใช้ Wilder เล็กน้อย (`indicators/atr.py`) |
| ทั่วไป | lookback ยาวสุดของ indicator ทุกตัว + ส่วนเผื่อ | แต่ละกลยุทธ์ควรประกาศค่านี้เอง |

ตัวเลขในตารางเป็นขั้นต่ำทางทฤษฎี ใช้ test ตัดหัว (ด้านล่าง) ยืนยันก่อนใช้จริง
หน้าต่าง live ควรใหญ่กว่าขั้นต่ำพอสมควร (ดึงข้อมูลครั้งละ 1000 แท่งเหลือเฟืออยู่แล้ว)

### Test ตัดหัว (เพิ่มในฉาก 5)
คำนวณสัญญาณจากข้อมูลเต็ม เทียบกับสัญญาณจากข้อมูลที่ตัดหัวทิ้ง k แท่ง
**หลังพ้นช่วง warm-up** สัญญาณต้องตรงกันทุกจุด ถ้าไม่ตรง = หน้าต่างเล็กเกิน
ผ่านทั้ง test ตัดท้ายและตัดหัว = พิสูจน์ได้ว่าสัญญาณ live ตรงกับ backtest

### คำถามที่ต้องตัดสินตอนฉาก 5: สัญญาณเป็น "เหตุการณ์" หรือ "สถานะ"?
- **เหตุการณ์ (event):** BUY เฉพาะแท่งที่เส้นตัดกัน (แบบที่ `sma_cross.py` ตั้งโจทย์ไว้ตอนนี้)
  - ข้อเสียฝั่ง live: ถ้าบอทล่มหรือรีสตาร์ทตรงแท่งนั้นพอดี สัญญาณหายไปเลย สถานะจริงกับที่ควรเป็นไม่ตรงกัน
- **สถานะ (state):** "ตอนนี้ควรถือ long" ทุกแท่งที่ fast > slow
  - ข้อดีฝั่ง live: รีสตาร์ทเมื่อไหร่ก็เทียบ "ควรถือ" กับ "ถืออยู่จริง" แล้วปรับให้ตรงได้เลย (idempotent)
  - ต้องคิดต่อ: ถ้าโดน stop loss แล้ว fast ยัง > slow จะเข้าใหม่ทันทีไหม
- ไม่ต้องตัดสินตอนนี้ แต่ถ้าเปลี่ยน ต้อง backtest ใหม่และเทียบผลกับแบบเดิม

**ตอนนี้ (ฉาก 2–4) ใช้แบบเหตุการณ์** เพราะเห็นภาพ "จุดตัด" ชัด และ `test_lookahead` ตรวจได้ตรง ๆ

#### ถ้าเปลี่ยนเป็นแบบสถานะ ผลจะต่างตรงไหน
สองแบบให้ผลไม่เท่ากันจริง ไม่ได้ต่างแค่วิธีเขียนโค้ด (สมมติ stop loss 2%):

| สถานการณ์ | แบบเหตุการณ์ | แบบสถานะ |
|---|---|---|
| แท่งแรกของข้อมูล/ต้นช่วง SMA20 อยู่เหนือ SMA50 อยู่แล้ว | ไม่ซื้อ รอจุดตัดรอบถัดไป | ซื้อที่แท่งถัดไปเลย |
| โดน stop กลางขาขึ้น (SMA20 ยังอยู่เหนือ) | รอจนตัดลงแล้วตัดขึ้นใหม่ อาจนานหลายสัปดาห์ | กลับเข้าแท่งถัดไปทันที อาจโดน stop ซ้ำหลายรอบ หรือตามเทรนด์ต่อได้ |

**ตอนเทียบผลให้ดู:** จำนวนไม้, ค่าธรรมเนียมรวม, max drawdown — กรณีกลับเข้าหลังโดน stop ทำให้สามตัวนี้ต่างกันมากที่สุด
และดูผลช่วงต้นของแต่ละช่วงข้อมูลแยก (กรณีแท่งแรก)

#### แปลงสองแบบไปมา
```python
import numpy as np

x = signals.map(lambda s: s.value)                     # Enum → ตัวเลข

# เหตุการณ์ → สถานะ (long อย่างเดียว: 1 = ถือ, 0 = เงินสด)
state = (
    x.replace(0, np.nan)
     .ffill()
     .fillna(0)                                        # ก่อนจุดตัดแรก = เงินสด
     .clip(lower=0)                                    # long อย่างเดียว: −1 → 0
)

# สถานะ → เหตุการณ์
events = state.diff().fillna(0)
```
โค้ดกลยุทธ์แทบไม่ต้องแก้ ส่วนที่ต้องทำใหม่จริงคือ backtest + journal ตามกฎ

หมายเหตุ:
1. **stop loss:** แปลงเหตุการณ์ → สถานะแบบนี้ไม่รู้เรื่อง stop loss — state ยังเป็น 1 หลังโดน stop
   ซึ่งก็คือพฤติกรรม "กลับเข้าทันที" ของแบบสถานะนั่นเอง
2. **`fillna(0)` ก่อนจุดตัดแรก:** หลัง `ffill` แถวก่อนสัญญาณแรกยังเป็น NaN (ไม่มีอะไรให้เติมไปข้างหน้า)
   → ตีความว่าถือเงินสด ตรงกับพฤติกรรม "ไม่ซื้อจนกว่าจะเห็นจุดตัด"
3. **`clip(lower=0)` สำหรับ long อย่างเดียว:** `ffill` เฉย ๆ ได้ 1/−1 ซึ่งแปลว่า long/short
   เราไม่มี short จึงตัด −1 เป็น 0 (ถือเงินสด) — ถ้าวันหนึ่งเพิ่ม short ให้ลบบรรทัดนี้
   และ `diff()` จะได้ ±2 ตอนกลับฝั่ง ต้องคิดใหม่
4. **แปลง Enum เป็นตัวเลขก่อน:** `Signal` เป็น Enum ใช้ `.replace(0, ...)` / `.diff()` ตรง ๆ ไม่ได้
5. **`events` เป็นตัวเลข (1, −1, 0) ไม่ใช่ Enum:** ถ้าจะส่งกลับเข้า engine ที่รับ `Signal`
   ให้ใช้ `events.astype(int).map(Signal)`
