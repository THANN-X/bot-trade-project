# Backtesting — กฎและกับดัก

## 1. Look-ahead bias

### กับดักชั้นที่ซ่อนอยู่: timestamp = เวลาเปิดแท่ง
ccxt ติดป้ายแท่งด้วย **เวลาเปิด** แท่ง `10:00` ของ timeframe 1h คือช่วง 10:00–11:00

```
ป้าย      ช่วงจริง        close รู้ค่าเมื่อไหร่
10:00  →  10:00–11:00  →  11:00
11:00  →  11:00–12:00  →  12:00
```

ถ้าเอา close ของแท่ง `10:00` ไปตัดสินใจ "ตอน 10:00" = แอบดูอนาคต 1 ชั่วโมง ทั้งที่ดูเหมือนทำตามกฎ

**กฎที่ใช้:** สัญญาณของแท่ง i คำนวณจากข้อมูลถึงแท่ง i → เข้าออเดอร์ที่ **open ของแท่ง i+1**
(open ของแท่ง `11:00` ≈ close ของแท่ง `10:00` ซึ่งเป็นเวลาที่เรารู้ข้อมูลครบจริง)

แท่งสุดท้ายที่ดึงมาจาก exchange มักยังไม่ปิด — ต้องตัดทิ้งก่อนใช้

### ทดสอบอัตโนมัติ (`tests/test_lookahead.py`)
1. คำนวณสัญญาณจากข้อมูลเต็ม
2. ตัดข้อมูลท้ายทิ้ง (ที่หลายจุด) แล้วคำนวณใหม่
3. สัญญาณในช่วงที่ซ้อนกันต้อง **เหมือนเดิมทุกจุด**

ถ้าเปลี่ยน = สัญญาณในอดีตขึ้นกับข้อมูลอนาคต = มี look-ahead
ทุกกลยุทธ์ต้องผ่าน test นี้ก่อนนับผล backtest

## 2. ค่าใช้จ่าย
| รายการ | ค่าเริ่มต้น | ที่มา |
|---|---|---|
| Fee | 0.1% ต่อข้าง | ใกล้ค่าจริงของ spot ส่วนใหญ่ |
| Slippage | 0.05% ต่อข้าง | สมมติฐานระมัดระวังสำหรับ BTC/USDT ขนาดไม้เล็ก — วัดจริงในฉาก 5 แล้วปรับ |

ค่าอยู่ใน `config/default.yaml` — อย่าเดาค่าอื่นเอง
ถ้ากลยุทธ์กำไรเฉพาะตอนค่าใช้จ่ายต่ำกว่านี้ ถือว่ายังไม่ผ่าน

### Stress test: slippage แย่ลง (ฉาก 3)
รัน backtest ซ้ำด้วย slippage **0.2%** แทน 0.05% (`costs.stress_slippage_pct`)
- ยังกำไร → มั่นใจขึ้นว่ากลยุทธ์ไม่ได้รอดเพราะสมมติฐานที่ดีเกินจริง
- กลายเป็นขาดทุน → กลยุทธ์เปราะเกินไป ยังไม่ผ่าน

รอบ stress บันทึกลง journal เหมือนรอบปกติ (ค่า `costs` ในบรรทัดนั้นจะบอกว่าเป็นรอบ stress)

### คำสั่งที่จำลอง
1. **ทุกคำสั่งใน backtest เป็น market order** ครอบคลุมการเข้าและออกไม้ทุกแบบ:
   | จังหวะ | ราคา | ดูเพิ่ม |
   |---|---|---|
   | เข้าไม้ | open ของแท่งถัดจากสัญญาณ BUY | §1 |
   | ออกด้วยสัญญาณ SELL | open ของแท่งถัดจากสัญญาณ | §1 |
   | ออกด้วย stop loss (stop-market) | ราคา stop หรือ open ถ้ากระโดดข้าม | §6 |
   | ปิดที่รอยต่อระหว่างช่วง | close ของแท่งสุดท้ายของช่วง | §3 |

   ทุกแถวหัก slippage + fee เหมือนกัน ไม่มีกรณีไหนเป็น limit order
2. **ไม่ใช้ limit order** เพราะต้องจำลองว่าได้ของหรือไม่ได้ ซึ่งแท่ง 1h บอกไม่ได้
3. **ไม่แยก maker / taker** คิดทุกคำสั่งเป็น taker 0.1% (market order คือ taker อยู่แล้ว)
4. **spread ไม่คิดแยก ถือว่ารวมอยู่ใน slippage 0.05%**
   ใช้ได้เพราะ spread ของ BTC/USDT บน Binance แคบมาก (~0.01 USDT, ครึ่ง spread ≈ 0.000006%)
   **ถ้าเปลี่ยนคู่เทรด ต้องวัด spread จริงก่อน** เหรียญที่ spread กว้างอาจเกิน 0.05% ด้วยตัวมันเอง

### ขนาดไม้ (`risk/sizing.py`)
```
entry         = ราคาเข้าที่ได้จริง = open × (1 + slippage)      ← engine คำนวณก่อนเรียก sizing
ขนาดไม้       = min( ตามความเสี่ยง , เพดานเงิน )
ตามความเสี่ยง = equity × risk_pct ÷ (entry − stop)
เพดานเงิน     = equity ÷ (entry × (1 + fee))  ≡  equity ÷ (open × (1 + slippage) × (1 + fee))
```
- **`entry` คือราคาที่ได้จริงเสมอ** ทั้งใน `sizing` และ `stops` — sizing จึงไม่รับ slippage
  (ถ้ารับ แล้ว engine ส่งราคาที่บวก slippage แล้วเข้ามา จะนับ slippage ซ้ำสองรอบ → เงินค้างไม่ได้ใช้
  ~0.05% ของพอร์ตทุกไม้ที่ชนเพดาน — `test_8c` กันไว้)
- **spot ไม่มี leverage** — ซื้อได้ไม่เกินเงินสดที่มี stop แคบ ๆ ทำให้สูตรตามความเสี่ยงสั่งซื้อเกินพอร์ตได้
- เพดานต้อง**หักค่าใช้จ่าย** และเป็นแบบ**คูณ** ไม่ใช่บวก `(1 + s + f)` เพราะ fee คิดจากราคาหลังบวก slippage
  แบบบวกจะจ่ายเกินเงินเล็กน้อย (พอร์ต 10,000 → เงินสดเหลือ −0.005) — มี test กันไว้ว่าเงินสดไม่ติดลบ
- ถูกตัดด้วยเพดาน → **ความเสี่ยงจริงต่ำกว่า risk_pct** ยอมรับได้ (กฎคือ "ไม่เกิน")
- นับจำนวนไม้ที่ถูกตัดไว้ใน journal (`n_capped`) — ถ้าเยอะ แปลว่า stop แคบเกินกว่าที่ risk_pct จะมีความหมาย

**ตัวอย่าง: พอร์ต 10,000, เสี่ยง 1%, เข้า 84,610, stop 84,310 (ห่าง 300)**
| | ค่า |
|---|---|
| ตามความเสี่ยง | 100 ÷ 300 = 0.333 BTC (≈ 28,200 USDT เกินพอร์ต) |
| เพดานเงิน | 10,000 ÷ (84,610 × 1.0005 × 1.001) ≈ 0.1180 BTC ← ใช้ค่านี้ |
| เสียจากราคาลง 300 | 0.1180 × 300 ≈ 35.4 USDT (0.35%) |
| **เสียจริงเมื่อโดน stop** (รวม slippage + fee ไปกลับ) | **≈ 65.3 USDT (0.65%)** — ต่ำกว่า 1% ที่ตั้งไว้ |

ค่าใช้จ่ายไปกลับ (~0.30% ของมูลค่าไม้) เกือบเท่ากับส่วนที่เสียจากราคา — stop ยิ่งแคบ ค่าใช้จ่ายยิ่งเป็นสัดส่วนใหญ่ของการขาดทุน

**ต่างจาก `kill_switch.safety.max_position_pct`:**
| | เพดานเงินในหัวข้อนี้ | `max_position_pct` |
|---|---|---|
| กันอะไร | ซื้อเกินเงินที่มีจริง (ข้อจำกัดทางกายภาพของ spot) | โค้ดมีบั๊กแล้วสั่งไม้ใหญ่ผิดปกติ |
| ใช้ตอน | ทุกไม้ ทั้ง backtest และ live | live / paper เท่านั้น (ฉาก 5) |
| ชนแล้ว | ตัดขนาดลง แล้วเทรดต่อตามปกติ | **หยุดบอททันที** รอคนตรวจ |
| ตัวเลข | คำนวณจาก equity และราคา | ตั้งตายตัวใน config (ยัง `null`) |

## 3. การแบ่งข้อมูล
```
|────────── จูน ──────────|──── ทดสอบ ────|─── holdout ───|
  เลือกพารามิเตอร์            walk-forward     แตะครั้งเดียว
```
- **จูน:** ลองพารามิเตอร์ได้ตามใจ (ทุกรอบบันทึกลง journal)
- **ทดสอบ:** ตรวจว่าพารามิเตอร์ที่เลือกยังใช้ได้กับข้อมูลที่ไม่เคยเห็น
- **holdout:** แตะได้ **ครั้งเดียว** ตอนเลือกกลยุทธ์เสร็จแล้ว ถ้าดูแล้วกลับไปแก้ holdout ก็กลายเป็นข้อมูลจูนไปแล้ว
- สัดส่วนอยู่ใน `config/default.yaml` (`splits:`)
- ตัวเลข kill switch เลือกจากช่วงจูนเท่านั้น

### คำนวณสัญญาณจากข้อมูลเต็มก่อน แล้วค่อยตัดตามช่วง
ถ้าตัดข้อมูลเป็นช่วงก่อนแล้วค่อยคำนวณสัญญาณ ต้นทุกช่วงจะเสีย warm-up ของ indicator
และเสียจุดตัดที่เกิดคาบรอยต่อ
ลำดับที่ถูก: `generate_signals(ข้อมูลเต็ม)` → ตัดทั้งราคาและสัญญาณตามช่วง → ส่งเข้า engine
ไม่ผิดกฎ look-ahead เพราะสัญญาณใช้แค่ข้อมูลอดีตอยู่แล้ว (`test_lookahead` ยืนยัน)

### กฎที่รอยต่อระหว่างช่วง
แต่ละช่วงวัดผลแยกกัน จึงต้องไม่มีอะไรข้ามรอยต่อ:
- **ทุกช่วงเริ่มด้วยพอร์ตว่าง** (เงินสดเท่า `initial_capital` ไม่มีไม้ค้าง)
- **ยังถือไม้ตอนแท่งสุดท้ายของช่วง → ปิดที่ close ของแท่งนั้น** หักค่าธรรมเนียมและ slippage ตามปกติ
- **ไม่ใช้สัญญาณของแท่งสุดท้ายของช่วง** เพราะจะเข้าไม้ที่ open ของแท่งถัดไป ซึ่งอยู่นอกช่วงแล้ว

### พฤติกรรมที่ตั้งใจ: แบบเหตุการณ์ไม่เข้าไม้ที่ต้นช่วง ถ้าเส้นตัดกันไปก่อนแล้ว
เช่น ช่วงทดสอบเริ่มตอนที่ SMA20 อยู่เหนือ SMA50 อยู่แล้ว (ตัดขึ้นไปตั้งแต่ในช่วงจูน)
→ ไม่มีจุดตัดในช่วงนี้ → **ไม่ซื้อ** รอจุดตัดขึ้นครั้งถัดไป
นี่คือพฤติกรรมของสัญญาณแบบเหตุการณ์ ไม่ใช่บั๊ก
ถ้าเปลี่ยนเป็นแบบสถานะในฉาก 5 จุดนี้จะเปลี่ยน (ดู `docs/decisions/0002-hexagonal-at-stage-5.md`)

## 4. Journal อัตโนมัติ (`docs/journal.jsonl`)
`scripts/run_backtest.py` เขียนต่อท้ายไฟล์เองทุกครั้งที่รัน **ห้ามลบหรือแก้บรรทัดเก่า**
รอบที่ผลไม่สวยสำคัญที่สุด — ถ้าต้องจดเอง จะลืมจดรอบนั้นแน่

หนึ่งบรรทัด = หนึ่งการรัน (JSON):
```json
{
  "run_at": "2026-10-01T08:30:00Z",
  "git_commit": "a1b2c3d",
  "git_dirty": false,
  "strategy": "sma_cross",
  "params": {"fast": 20, "slow": 50},
  "data": {"symbol": "BTC/USDT", "timeframe": "1h", "start": "...", "end": "..."},
  "split": "tune",
  "costs": {"fee_pct": 0.001, "slippage_pct": 0.0005},
  "results": {"net_profit": 0, "expectancy": 0, "profit_factor": 0, "max_drawdown": 0,
              "win_rate": 0, "n_trades": 0, "n_capped": 0, "max_losing_streak": 0,
              "worst_day_pct": 0}
}
```
- `n_capped` = จำนวนไม้ที่ขนาดถูกตัดด้วยเพดานเงิน (หัวข้อ 2 "ขนาดไม้")
- `git_dirty: true` = มีโค้ดที่ยังไม่ commit ตอนรัน → ผลนั้นย้อนกลับไปทำซ้ำไม่ได้แน่นอน
- ใช้ตรวจ: ลองไปกี่ชุดแล้ว (overfitting), แตะ holdout ไปกี่ครั้ง, cool-off ครบ 1 เดือนหรือยัง

## 5. โครง engine — แบบผสม
แยกงานเป็นสองจังหวะ แต่ละจังหวะใช้วิธีที่เหมาะกับมัน:

| จังหวะ | วิธี | ทำไม |
|---|---|---|
| 1. คำนวณสัญญาณ | pandas ทั้งตารางครั้งเดียว (`strategy.generate_signals(df)`) | indicator อย่าง SMA ไม่ขึ้นกับว่าเราถือไม้อยู่หรือเปล่า → คำนวณรวดเดียวได้ เร็วและอ่านง่าย |
| 2. เข้า/ออกไม้ | loop ทีละแท่งใน `backtest/engine.py` | ขนาดไม้, stop loss, kill switch ขึ้นกับ equity และสถานะ ณ แท่งนั้น (path-dependent) → ต้องเดินทีละแท่ง |

ตัวอย่างว่าทำไมจังหวะ 2 คำนวณทั้งตารางไม่ได้: ขนาดไม้ไม้ที่ 10 = 1% ของ equity หลังไม้ที่ 9
ซึ่งรู้ได้ก็ต่อเมื่อจำลองไม้ 1–9 เสร็จแล้ว

ข้อดีเพิ่ม: จังหวะ 1 ยังเป็นโค้ดบริสุทธิ์ → `test_lookahead` ตรวจได้ตรง ๆ
และตอนฉาก 5 loop ของจังหวะ 2 คือส่วนที่จะย้ายเข้าแกนกลาง (`docs/decisions/0002-hexagonal-at-stage-5.md`)

## 6. Stop loss — กฎการเติมราคา (fill)
หัวข้อ 5 พูดเรื่องโครง engine ส่วนหัวข้อนี้คือ "ออกไม้ได้ที่ราคาเท่าไหร่" (long อย่างเดียว)

### กฎ
เช็คทุกแท่งที่ถือไม้อยู่ ตามลำดับนี้:
1. **open ≤ stop** (ราคาเปิดกระโดดข้าม stop) → ปิดที่ **open**
   ไม่ใช่ที่ราคา stop เพราะไม่เคยมีช่วงไหนที่ราคาอยู่ตรง stop ให้ขายได้จริง
2. ไม่อย่างนั้น ถ้า **low ≤ stop** → ปิดที่ **ราคา stop**
3. หัก **slippage** ทั้งสองกรณี (ขาย → ได้ราคาต่ำกว่า) แล้วหัก **fee 0.1%** จากราคาออกตามปกติ

### ตัวอย่าง: stop 60,000, slippage 0.05%
| กรณี | ราคาออกก่อนหัก slippage | หลังหัก slippage |
|---|---|---|
| open 60,300, low แตะ 59,800 | ที่ stop 60,000 | 60,000 × 0.9995 = 59,970 |
| open 59,500 (เปิดต่ำกว่า stop เลย) | ที่ open 59,500 | 59,500 × 0.9995 = 59,470.25 |

แถวที่สอง ถ้าใช้กฎผิด (ปิดที่ราคา stop) จะได้ 59,970
→ **ขาดทุนน้อยกว่าความจริงประมาณ 500 USDT ต่อ 1 BTC จากไม้เดียว** (59,970 − 59,470.25 = 499.75)

**ข้อจำกัดที่กฎนี้ยังไม่ครอบคลุม:** ตลาดคริปโตเปิด 24 ชม. gap ระหว่างแท่ง 1h จึงเกิดน้อย
แต่ช่วงข่าวแรง ราคาอาจทะลุ stop **ภายในแท่ง** แล้วได้ราคาแย่กว่า slippage 0.05% ที่สมมติไว้
→ กรณีแถวแรกในความจริงอาจได้ต่ำกว่า 59,970 — วัด slippage จริงในฉาก 5 แล้วปรับ (หัวข้อ 2)

**หลักฐานจากข้อมูล 2 ปี** (BTC/USDT 1h, 2024-09-29 → 2026-09-29, `notebooks/01_data_check.py`):
- gap ระหว่างแท่งใหญ่สุด **0.016%** (~14 USDT, 2025-03-03 15:00) — เล็กกว่า slippage 0.05%
  → กฎข้อ 1 (open ข้าม stop) แทบไม่มีผลกับคู่นี้
- แท่งที่แกว่งแรงสุด **2025-10-10 21:00**: open 114,267 → low 102,000 ใน 1 ชม. (range 11.5%, median ทั้ง 2 ปี 0.5%)
  → stop-market ที่โดนในแท่งแบบนี้ได้ราคาแย่กว่า 0.05% ได้มาก — นี่คือความเสี่ยงจริง ไม่ใช่ gap
- ราคาขึ้น ~21% ใน 3 วัน (19–21 ส.ค. 2026) เป็นการไหลทีละแท่งพร้อม volume ×3–4 ไม่ใช่ gap
  → ถ้าเกิดในทิศลง กฎข้อ 2 (low แตะ stop) คือตัวที่ทำงาน

fee คิดจากราคาหลังหัก slippage: แถวแรก ≈ 59.97, แถวที่สอง ≈ 59.47 USDT ต่อ 1 BTC

### ราคา stop (`risk/stops.py`)
- **วัดจากราคาเข้าที่ได้จริง** (open แท่ง i+1 หลังบวก slippage) ไม่ใช่จาก open — ระยะ stop จึงตรงกับเงินที่จ่ายจริง
  และ "เสีย 1% ตอนโดน stop" แม่นกว่า
- เลือกวิธีจาก `risk.stop_method` ใน config:
  | วิธี | ราคา stop | สถานะ |
  |---|---|---|
  | `pct` | ราคาเข้า × (1 − `stop_pct`) — เริ่มที่ 2%, จูนในฉาก 3 | ใช้อยู่ |
  | `atr` | ราคาเข้า − `atr_mult` × ATR(`atr_period`) | ขั้นที่สองของฉาก 2 — หลัง engine เขียวครบ |
- **ATR ต้องใช้ของแท่งสัญญาณ i ไม่ใช่แท่งเข้า i+1** — ATR ของแท่ง i+1 ใช้ high/low/close ของแท่งนั้น
  ซึ่งยังไม่รู้ตอนส่งคำสั่งที่ open → look-ahead; ATR ต้องผ่าน test look-ahead แบบเดียวกับกลยุทธ์
- `stop_method` ที่ไม่รู้จัก → error ทันที (แบบเดียวกับ side ใน costs.py)

### ประเภทคำสั่ง: stop-market เท่านั้น
backtest จำลอง **stop-market** (ถึง stop แล้วขายทันทีที่ราคาตลาด)
ตอน live ในฉาก 5 ต้องใช้ stop-market ด้วย **ห้ามใช้ stop-limit**
เพราะวันที่ราคากระโดดข้าม stop คำสั่ง stop-limit อาจขายไม่ได้เลย
ผลจริงจะต่างจาก backtest ตรงวันที่ขาดทุนหนักที่สุดพอดี

ถ้า exchange ไม่รองรับ stop-market ให้บอทเฝ้าราคาเองแล้วส่ง market order เมื่อถึง stop (ตัดสินใจในฉาก 5)

### แท่งที่เพิ่งเข้าไม้
เราเข้าที่ open ของแท่งนั้นพอดี (และ stop อยู่ต่ำกว่าราคาเข้าเสมอ) ราคาจึงกระโดดข้าม stop ไม่ได้
→ ข้ามข้อ 1 ไปเลย ถ้า low ของแท่งเดียวกันลงไปแตะ stop ให้ **ปิดที่ราคา stop ภายในแท่งนั้นเลย**

### หลังโดน stop (สัญญาณแบบเหตุการณ์)
- ถือเงินสด รอ BUY ครั้งถัดไป ไม่กลับเข้าทันที แม้ SMA20 ยังอยู่เหนือ SMA50
- ได้ SELL ตอนไม่มีไม้ → ไม่ทำอะไร
- เหตุผลและผลที่ต่างจากแบบสถานะ: `docs/decisions/0002-hexagonal-at-stage-5.md`

## 7. ตรวจข้อมูลก่อน backtest
รัน `notebooks/01_data_check.py` **ทุกครั้งที่ดึงข้อมูลใหม่หรือเปลี่ยนคู่เทรด / timeframe** ก่อนเอาไป backtest

| ตรวจ | ผ่านเมื่อ | ถ้าไม่ผ่าน |
|---|---|---|
| แท่งหาย | ทุกแถวห่างกันเท่ากับ timeframe พอดี | ตัดสินใจก่อน backtest ว่าจะตัดช่วงนั้นหรือเติม แล้วจดลงหัวข้อนี้ |
| gap ใหญ่สุด | เล็กกว่า `costs.slippage_pct` | กฎ "open ข้าม stop" (หัวข้อ 6) จะมีผลจริง — ดูว่าเกิดตรงไหน บ่อยแค่ไหน |
| range / แท่งสุดโต่ง | ดูไว้ ไม่มีเกณฑ์ตายตัว | จดวันที่แท่งสุดโต่งไว้ — ใช้ตรวจว่า backtest ถือไม้อยู่ตอนนั้นไหม |
